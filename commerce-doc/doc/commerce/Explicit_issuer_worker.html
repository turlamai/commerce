8 Explicit issuer worker🔗ℹ

Server processes explicitly require "commerce/issuer.rkt". This module imports the published permit/issuer signing surface; the default facade never does. The worker owns no durable state: every decision derives from the claimed outbox row, the pinned catalog, and recorded lineage.

(make-issuance-worker

 #:catalog catalog #:issuer issuer

 #:private-key private-key #:key-id key-id

 #:trust-store trust-store

 [#:clock clock] [#:owner owner]

 [#:lease-seconds lease-seconds]

 [#:transient-backoff-seconds transient-backoff]

 [#:operator-backoff-seconds operator-backoff])

  -> issuance-worker?

Binds one reviewed catalog, issuer identity, Ed25519 private key, trust store key id, and trust store behind one opaque worker value. The private key is never exposed by an accesssor. The clock returns two values, an epoch second and its RFC 3339 string; the default reads wall-clock UTC.

(process-issuance-work! worker storage)

  -> (or/c issuance-result? #f)

Claims one due outbox row and drives it: deterministic dead ends are released with their typed commerce code and an operator backoff before any signing; a grant with no lineage signs revision zero and a withdrawal signs an issuance-expiring successor naming the latest revision; the exact recorded bytes are signed outside the claim transaction, and the revision, the signed envelope, and a one-time claim are recorded in one transaction. The result’s claim token is delivered to the caller exactly once for a single customer handoff. Returns #f when nothing is due. Dispositions: ’completed with the storage completion record and claim token, ’released with the typed error code, or ’lease-lost when the lease expired between claim and completion, in which case nothing was written. Permit signing failures release as ’permit-issue-failed with the transient backoff; the same durable work completes after repair.

(derive-entitlement-id issuer subject-type subject-id offer-id)

  -> string?

 

(derive-credential-id entitlement-id revision)

  -> string?

Deterministic lineage and credential identifiers. Reprocessing never allocates a second lineage or revision; a crash after signing converges because Ed25519 re-signs identical bytes to an identical signature.

8.1 One-time claim delivery🔗ℹ

The issued credential record retains the exact signed envelope bytes; the claim stores only the token’s SHA-256 digest. No transport or HTTP listener is included in this boundary.

(storage-claim-credential storage #:token token #:now now)

  -> claim-fulfillment?

Verifies the token, its state, and its fulfillment window, marks the claim claimed, and returns the claim id, the fulfillment time, and the issued-credential-record with the exact signed envelope bytes, which verify as a Permit envelope for the recorded key id. Wrong, reused, and expired tokens raise typed exn:fail:commerce values (’claim-not-found, ’claim-already-claimed, ’claim-expired) and mutate nothing. Fulfillment never creates or advances a lineage revision.

(storage-mark-claim-notified storage #:token token #:now now) -> void?

Records that a delivery transport handed the token out. The first notification timestamp wins; later retries are idempotent no-ops.

(storage-complete-issuance-work! storage item ...

 [#:signed-credential-bytes envelope-bytes]

 [#:key-id key-id]

 [#:claim-token claim-token]

 [#:claim-expires-at claim-expires-at])

The optional delivery half of completion: when the exact signed envelope bytes and key id are supplied, the completion transaction also records the issued credential; a claim token and expiry add its one-time fulfillment claim. Omitting them records issuance evidence without delivery, as before.
