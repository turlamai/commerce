7 Offer-to-Permit policy mapping🔗ℹ

Server processes explicitly require "commerce/permit.rkt". This module imports the published permit/issuer snapshot surface; it is not re-exported from the default facade and never accesses a signing key.

(make-permit-grant-policy

 [#:products products]

 [#:product-families product-families]

 [#:edition edition]

 [#:feature-policy feature-policy]

 [#:features features]

 [#:addons addons]

 [#:capabilities capabilities])

 -> permit-grant-policy?

Constructs one reviewed grant policy. Optional Commerce values use #f; the adapter translates absence to Permit null. The smart constructor validates the resulting grant through Permit’s complete entitlement schema. Feature policy is ’explicit or ’published-through.

(make-permit-policy-catalog

 offers policies

 [#:deleted-offer-ids deleted-offer-ids])

 -> permit-policy-catalog?

Policy ids are immutable revisions; the positive integer version is audit metadata and never selects a mutable latest policy. The catalog contains both active and retained retired Offer definitions. Explicit deletion tombstones are distinct from never-known Offer ids. Every Offer’s product must occur in the explicit product scope of its pinned policy.

(prepare-permit-snapshot

 catalog intent

 #:issuer issuer

 #:credential-id credential-id

 #:entitlement-id entitlement-id

 #:issued-at issued-at

 [#:previous previous])

 -> permit-snapshot-request?

For ’grant, creates a complete entitlement at revision 0 and rejects an existing lineage. For ’withdraw, requires the previous complete snapshot, checks issuer, entitlement id, subject, type, and grants, advances its revision, and sets use_expires_at to the new issued_at. This communicates an issuance-expiring successor to connected clients; it does not revoke an old offline credential.

The result exposes policy id/version, action, source idempotency key, the validated complete payload, and permit-snapshot-request-payload-bytes. The payload tree and bytes are immutable copies. Those bytes are Permit’s single serialization and are the only bytes a later signer may sign. Unknown/deleted Offers, invalid policy/catalog/request data, unsupported actions, and missing or conflicting lineage raise typed exn:fail:commerce values. The optional #:use-expires-at overrides the successor’s use_expires_at: a withdrawal for a subscription order expires at the paid-through moment (cancellation at period end), and the ’renew action — a successor over the previous revision of the same lineage — requires it. No outbox mutation, lineage persistence, signing, or delivery happens in this operation.

(permit-policy-for-offer catalog offer-id)

  -> permit-entitlement-policy?

Resolves the pinned policy for one Offer with the same typed failures as snapshot preparation, so a worker can fail before signing.
