6 Durable projection and issuance outbox🔗ℹ

Journal acknowledgement and projection are separate durability phases. Projection runs outside the provider request:

(storage-project-next! storage #:processed-at processed-at)

  -> (or/c projection-result? #f)

  processed-at : exact-nonnegative-integer?

Selects the lowest unprocessed journal sequence and atomically writes its order projection, any newly emitted issuance-outbox row, and its processing marker. It returns #f when no sequence is pending. A successful result has disposition ’projected; an order identity conflict has disposition ’blocked, failure code ’order-conflict, no new outbox items, and leaves the previous order unchanged.

(storage-order-ref storage provider order-id)

  -> (or/c order-projection? #f)

 

(storage-outbox-ref storage idempotency-key)

  -> (or/c issuance-outbox-item? #f)

 

(storage-close storage) -> void?

projection-result exposes disposition, journal sequence, resulting order, new outbox items, and optional failure code. Each issuance-outbox-item exposes its stable idempotency key, source sequence, rights action and commercial identifiers, occurrence time, and workflow state. New rows are ’pending with zero attempts and no lease. Call storage-close during service shutdown.

6.1 Issuance lease state machine🔗ℹ

The issuance worker protocol is owner-safe: a row is claimed, signed work happens outside the claim transaction, and completion or release re-checks the lease owner against the database.

(storage-claim-issuance-work! storage

 #:owner owner #:lease-seconds lease-seconds #:now now)

  -> (or/c issuance-outbox-item? #f)

Claims the lowest due outbox row in one immediate transaction: status ’processing, attempts incremented by one, and an opaque exclusive lease bound to the owner. A row is due when it is ’pending and available_at <= now, or when its lease has expired. Returns #f when nothing is due.

(storage-complete-issuance-work! storage item

 #:issuer issuer #:subject-type subject-type

 #:entitlement-id entitlement-id #:credential-id credential-id

 #:policy-id policy-id #:policy-version policy-version

 #:payload-bytes payload-bytes #:issued-at issued-at

 #:recorded-at recorded-at)

  -> issuance-completion?

Appends the lineage root together with revision zero, or exactly one successor revision, and completes the outbox row inside the same short transaction. The writer enforces the ADR-0008 identity rules as typed failures before any insert: a second grant over an existing lineage, a commercial identity bound to a different entitlement, a withdrawal without a lineage, and a credential id already bound to another revision raise exn:fail:commerce codes ’entitlement-lineage-conflict or ’entitlement-lineage-required and write nothing. The payload digest is computed from the given bytes, never trusted from the caller. Completion without the active lease raises ’lease-not-held. Repeating a completion that already landed reconciles to the recorded revision; the same outbox id with different payload bytes is a conflict.

(storage-release-issuance-work! storage item

 #:error-code error-code #:retry-at retry-at)

  -> issuance-outbox-item?

Returns transient work to ’pending with the typed error code recorded and a future retry time. Only the lease owner may release; attempts stay exactly as the claim incremented them.

(storage-entitlement-ref storage entitlement-id)

  -> (or/c entitlement-lineage? #f)

 

(storage-lineage-ref storage #:issuer issuer #:subject-type subject-type

 #:subject-id subject-id #:offer-id offer-id)

  -> (or/c entitlement-lineage? #f)

 

(storage-entitlement-revision-ref storage entitlement-id revision)

  -> (or/c entitlement-revision? #f)

 

(storage-latest-entitlement-revision storage entitlement-id)

  -> (or/c entitlement-revision? #f)

 

(storage-latest-entitlement-revision-and-unresolved-refund

 storage entitlement-id subject-id offer-id)

  -> (values (or/c entitlement-revision? #f) boolean?)

Readers expose durable lineage and revision state for worker snapshot preparation, crash reconciliation, and audit. The combined revision and refund reader returns both mutable facts from one consistent read transaction: hosted proof verification denies on freshness and refund state together, so reading them separately could straddle the transaction that records a withdrawal and serve a withdrawn grant. Revision payload bytes are the exact unsigned snapshot bytes, never signed credential bytes. No Permit signing, signed-credential persistence, claim delivery, or HTTP listener is included in this boundary.
